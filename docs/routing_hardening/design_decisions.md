# Final routing contract decisions

2026-09-13. Implements the narrow direction reviewed in [contract_review.md](contract_review.md). The decisions originated in Stage 1; completed production adoption and its limits are recorded in [the execution ledger](implementation_status.md).

`runRoutingLifecycle` is the only final route-set coordinator. Its previous per-connector interface had no production callers and is replaced, along with its synthetic metadata-validity test. Journey retains `solveRoutingClaims`, an assignment-only API. Existing occupancy wrappers remain assignment preparation until each adopter migrates; they do not certify final geometry.

`FinalRoutingContext` contains all connectors, independent adapter-resolved endpoints and sides, per-end marker/stub clearance, node boxes, declared blockers, finite canvas bounds, logical-run resource bounds/locks, priority and scoped sharing/crossing policy. Final validation has no interaction-exclusion flag. It checks endpoint-box reentry as well as initial attachment. Accepted points are cloned and frozen. `resolved` alone exposes `routeByConnectorId`; failure exposes only `debugConnectors`, violations and bounded-exhaustion reason.

Span dependencies use deterministic candidate generation with reconstruction and complete revalidation, not frozen-span assignments iterated against stale geometry. Within unchanged topology, logical run IDs derive from terminal role and axis ordinal. A geometry revision owns one run coordinate; both adjacent bends change together. A normalization changing topology creates a new candidate and cannot reuse index locks. Hard endpoint/resource/topology locks remain constraints; heuristic prepared coordinates remain preferences. All physical spans and full-route interactions are rebuilt after a candidate change.

Initial valid input returns unchanged. Otherwise candidate preference orders hard-violation improvement during exploration, avoiding expansion, unrelated movement, priority-weighted displacement, penalized crossings, bend count, length and a stable canonical tie-break. Hard violations never qualify for acceptance at any score. Search is finite: 4096 reconstructed candidate evaluations and 128 expanded geometry revisions per final call; counters do not reset at expansion. Duplicate canonical geometry is not progress. The larger candidate budget than the review's provisional 256 allows event-derived turn alternatives across the complete measured scene; required proof tests will determine whether this bound is sufficient. Low-level assignment keeps its existing 100,000-state per-component ceiling and Journey's specialized override.

Expansion callback returns rebuilt complete context from the adapter's stable layout baseline. Requests/application counts are absolute, monotonic and share the existing owner/ceiling: four Outcome/Service, eight Scenario. A missing owner or exhausted legal candidates produces failure, never a geometric impossibility claim. The exact Outcome proof must succeed without callback expansion or moved nodes/ports/canvas.

16px/0.5px interval acceptance remains unchanged. A marked end requires at least 12px (current arrow footprint extends 9px inward at the default 10px paint size); larger theme arrows need their actual paint footprint included by the adapter/shared marker metric. Zero is permitted only at an unmarked end without a port stub. Perpendicular `allow` is permitted, `penalize` contributes candidate cost, `forbid` rejects, and marked crossing policy requires current marks. No same-source/target sharing exception is introduced.

No semantic bundle additions are required by the captured Outcome repair. Existing channels/priority continue through `core/views.yaml` → loaded view → render model → staged adapter. Any newly needed semantic sharing/port permission must pass the bundle gate first. Adapter blockers are actual prohibited headers/reservations, not all containers or separators inferred from appearance.

Executable Stage 1 evidence: `tests/routingHardeningAcceptance.spec.ts` independently checks 1.5/14.5/tolerance separation, actual accepted geometry, unchanged valid routes, failure result shape, required points, independent endpoints, declared sides, both marker ends, resource bounds and endpoint-box reentry. `stage1-contract.log`: 20 tests passed, including 12 existing core tests after replacing the mock-validity test. `tests/routingHardeningAssignment.spec.ts` initially reports eight failures (`stage1-red.log`), left visible for Stage 2 implementation. The coordinator initially rejects invalid input; geometry repair readiness and production adoption remain separate unaccepted gates.

Review hardening: accepted results include the exact accepted context for adapters whose expansion changes layout. Expansion receives a matching geometry/violation revision, cannot discard or weaken absolute logical-run bounds/locks or change sharing ownership, and cannot weaken the initial policy. Current per-run constraints are absolute; a relocatable locked resource would require an explicit typed reference before an adapter can use it. Outcome's root free-space bound is represented by context bounds, avoiding duplicate per-run scalar constraints. Continuity marks are accepted for their declared revision and cleared when generic repair changes geometry; the final lifecycle does not invent marks.

Outcome preparation and final resolution share four effective layout expansions. Requests after the final occupied row/column are ineffective for the existing cell-shift owner and no longer consume attempts. This is a no-progress correction, not a larger expansion budget.

Final assignment preparation keeps connectors outside the initial violated component fixed, while retaining their full segments as constraints; reconstructed interactions can widen the affected set in later revisions. Expansion receives a detached copy so in-place rebuilding cannot mutate away the original locks or endpoint requirements. The four/eight expansion ceilings predate this work and are explicitly retained by plan §5.5. They bound recomputation passes, not the size of a measured capacity increment, and do not assert completeness for arbitrary diagrams.

## Shared overlap topology recovery (2026-10-07)

Corridor reconstruction has two lifecycle paths. Existing atomic recovery rebuilds connectors implicated in blocking violations together; a one-connector revision could otherwise leave other hard-invalid routes that cannot enter the queue. A private overlap-alternative generator instead offers one reconstructed connector at a time when the complete current state has only traversable violations and the connector is implicated in `collinear_overlap` or `track_separation`. Remaining traversable conflicts can enter the same queue and compose into later repairs.

Both paths use the existing `buildPortCorridorCandidates` generator. Its declared-port construction and eligibility restrictions remain authoritative: straight routes, nonempty logical-run constraints, and topology-bound shared-track ownership do not gain permission to rebuild. Every candidate revision clears crossing marks across the complete connector set; generic repair cannot carry marks from an earlier geometry arrangement.

Overlap alternatives run within a popped repair revision after existing assignment/terminal-turn candidates have failed to produce a valid result. They use the same canonical deduplication, complete-context validation, scoring, queue gate, and global candidate/revision budgets as turn alternatives. A valid assignment or turn remains preferred before new topology is considered. Candidate budgets are not reserved or reset for the new family: a dense turn search can still exhaust the bounded search before corridor alternatives are reached.

This is a shared renderer geometry repair under existing port permissions, with no new bundle convention or public API. The v0.2 reconverging ScenarioStep fixture proves the previously excluded failure class; it does not identify the exact cause of an unavailable original document. Acceptance evidence and label-placement limits are recorded in the execution ledger.

## Shared label capacity and Scenario correction (2026-10-07)

Scenario now opts into shared connector-label assessment, final audit, and physical-corridor capacity measurement. Existing Outcome, Service and UI Contracts callers retain their placement defaults. Association requires a nonzero segment of the label's own route, at most the existing 12px label distance, and projected overlap of at least the minimum of 24px, label extent and segment length. Both axes are supported; a label centered on its own route remains legal. Actual node/header/marker footprints, other connectors, label clearance, adapter-declared separators, bounds and geometric scope are audited independently of placement fallback flags.

The Scenario adapter gives cross-row labels the vertical envelope of their endpoint nodes. Empty canvas below the rows cannot substitute for a connector label lane. Invalid placements are reconsidered against all usable actual route segments; valid placements are retained. Labels and their supporting routes generate one combined capacity claim per corridor. A single prospective anchor is selected before projecting demand into both axes. First-fit interval packing reuses tracks for disjoint spans, accounts for measured label dimensions and clearance, and returns deficits under opaque layout-owner identifiers. Boundary requirements merge by maximum; cumulative changes across revisions add to the stable original baseline.

The lifecycle is explicit: prepare measured layout and routes, accept complete connector geometry through `runRoutingLifecycle`, assess labels, request effective measured capacity, rebuild endpoints/routes/decorations, and audit again. Preparation, routing expansion and label correction share eight effective expansions. Requests after the last occupied boundary and geometry-preserving rebuilds cannot consume further effective expansions. Repeated states stop correction. Routing candidate and revision consumption is carried across calls using the existing 4096/128 limits; zero remaining candidate budget cannot enter the lifecycle's minimum-one clamp.

Each accepted revision saves its complete scene, prepared routes, accepted context, labels, gutter state and optional-exit ownership. Best-scene preference orders missing labels, collision/bounds problems, detachment count, detachment distance, canvas area and earliest revision. Later routing failure discards that attempted revision. The user-selected degraded-output policy publishes the best previously route-valid scene with one `warn` diagnostic per unresolved label, including stop reason and capacity evidence. Initial routing failure retains error diagnostics and blocks artifact publication. Warning-only SVG and SVG-derived PNG remain available. Displayed labels are preserved rather than silently omitted.

`finalResolutionTrace` still describes the selected routing call. Scenario's `labelLayoutTrace` separately reports aggregate search consumption, expansion counts by cause, selected revision, termination and unresolved label IDs. The exact emitted scene is revalidated before serialization. This is renderer geometry under existing bundle-owned display/port policies; it adds no language, bundle convention, CLI option or legacy-backend behavior. Fixed-geometry shared overlap recovery remains independently tested, while complete Scenario rendering may now expand layout to fit labels.
