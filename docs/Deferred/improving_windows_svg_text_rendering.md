Yes—but there is no SVG/CSS switch that forces macOS-style antialiasing or supersampling. For live SVG `<text>`, the Windows viewer ultimately controls rasterization, using either ClearType or grayscale antialiasing depending on the browser, transparency, and compositing.

`text-rendering: geometricPrecision` is expected to hurt: SVG explicitly defines it as favoring outline precision and usually disabling font hinting. Use `auto`; optionally test `optimizeLegibility`, although it remains only a hint. [SVG 2 rendering hints](https://www.w3.org/TR/SVG2/painting.html#TextRenderingProperty)

The large-`viewBox` trick will not reliably supersample. Browsers normally transform vector geometry into final device coordinates and rasterize at the displayed size; they do not promise to render a large intermediate bitmap and downsample it. CSS downscaling can even introduce compositing or blur.

The most promising issue in this repository is more concrete: the renderer embeds only `PublicSans-Regular.woff`, declared as weight 400, but titles and badges request weight 600:

- The embedded face defaults to 400 in [svgArtifacts.ts](./src/renderer/svgArtifacts.ts:49).
- Only that single face is embedded by [svgBackend.ts](./src/renderer/staged/svgBackend.ts:598).
- The theme requests weight 600 in [theme.ts](./src/renderer/staged/theme.ts:124).

That leaves the viewer synthesizing semibold from Regular. Synthetic weight can look substantially rougher on Windows.

I would prioritize:

1. Embed genuine Regular 400 and Semibold 600 faces:

```css
@font-face {
  font-family: "Public Sans";
  src: url(...) format("woff");
  font-weight: 400;
}

@font-face {
  font-family: "Public Sans";
  src: url(...) format("woff");
  font-weight: 600;
}

text {
  font-synthesis: none;
  text-rendering: auto;
}
```

2. As a quick diagnostic, set the current 600-weight roles to 400. If Windows improves markedly, synthetic weight is the primary culprit.

3. Try an opaque root background:

```svg
<rect width="100%" height="100%" fill="#fff"/>
```

ClearType is generally unsuitable for transparent render targets; Windows may automatically switch those surfaces to grayscale antialiasing. An opaque background can therefore change the result in some viewers. [Microsoft’s Direct2D alpha/ClearType documentation](https://learn.microsoft.com/en-us/windows/win32/direct2d/supported-pixel-formats-and-alpha-modes)

4. Avoid fractional whole-SVG scaling and evaluate at 100% browser zoom. Your 12–13 px roles are especially sensitive to pixel phase; moving them to 14 px would likely help more than rendering CSS.

The existing Regular WOFF does contain TrueType hinting tables, so the Regular font is not simply unhinted. The missing real 600 face is the more suspicious defect.

If identical Mac/Windows appearance is an absolute requirement, convert glyphs to paths. That bypasses platform font hinting and synthetic weights, but sacrifices selection, search, accessibility, and compactness. Otherwise, the viewer’s Windows rasterizer does indeed have the last word.
